# Task16A Matrix account deletion source acceptance

This note records local Chat source checks through `d026e49c24351e51298e1565441f60e91bc38cae`. It is source and fixture acceptance only. It does not certify a deployed deletion service, live browser/device flow, host-wide account deletion or store review.

## Implemented boundary

- Matrix deactivation uses the captured SDK `Client`, account generation, homeserver, exact password, and frozen server-erasure choice. The UIA coordinator decodes real `MatrixException` challenge fields even when no HTTP response object is attached, retains session/completed stages, offers only eligible stages, bounds retries, and rejects malformed, expired, replaced or foreign challenges. Browser fallback is built from the trusted homeserver and original operation; returning from the browser only retries the server request. It never supplies a deletion receipt.
- A real successful `Client.deactivateAccount` Future is the only source of a server-confirmed receipt. The operation records that success before local cleanup, including when cancellation or account replacement occurs while the request is in flight. Only the original generation can clear its SDK client, session, saved account/index and local room-key snapshot. Deletion uses neither ordinary logout, which can preserve keys, nor global purge. A new B or new A generation is never cleaned by an old A receipt.
- SDK `Client.clear` and manager initialize/force-reinitialize/dispose share a narrow lifecycle gate. A controlled SQLite FFI fixture reproduced an old clear erasing a marker saved in a reopened same-name database before the fix; the same fixture verifies preservation after the gate. This used a temporary test database, not a real account or installed device.
- Security Settings has the visible password/multistage/fallback flow and a pending-cleanup entry. A failed local cleanup retains a versioned, credential-free identity journal when writable. If the journal write itself fails, the same mounted page retains the confirmed in-memory receipt and offers a retry without another server request. The pending retry captures one session and excludes a concurrent new deletion. A completed original-generation cleanup alone dispatches the deletion-specific authenticated-state transition and returns to the root route.
- SDK native OIDC is identified by its stored `oidc_client_id`; its advertised HTTPS account-management link may be opened, but that handoff does not confirm deletion or clear local data. Legacy Matrix and ordinary social-login sessions use the UIA route. This preserves the existing IAP, subscription, NFT, redpacket and wallet flows.

## Remaining acceptance

- Matrix 13 exposes `MatrixSdkDatabase.delete()`, but the version-1 pending journal does not record a verifiable old database owner/name/path. After process death, A→B or ABA, a current same-identity index mapping may belong to new A; null-device sessions are not indexed. The visible retry therefore leaves inactive old A cleanup pending rather than guessing a database to delete. If the journal write fails and the process dies before retry, the in-memory receipt is lost; there is no durable retry proof for that case.
- Live homeserver UIA and native browser return, native/device secure storage, account-management web completion, host Git-pin integration and deletion of non-Matrix host services remain unverified. A Matrix protocol acknowledgement does not prove federated-copy erasure or operator/store-policy compliance. No production deletion or real account action was performed for this source work.
